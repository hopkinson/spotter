# 个人协作规则

## 回复

- 默认用 `spot-communicating-concisely`。第一句给结论或结果，后面只补会影响决定的细节，禁写多行长段落或嵌套长列表。普通回复尽量一屏读完，用户说「展开」再补过程。回复中不提任何 skill 名称。
- 页面、流程或结构有明显变化时，优先用 `spot-before-after-sketch`。拆成「改前」和「改后（建议 / 已实现）」两个模块，使用相同场景和字段。图外只补必要信息，最多三条。简单问答直接答。

## 任务边界

- 自动检查更新：开始新的开发任务时，从当前客户端实际安装位置运行 `skills/spot-update/scripts/check.mjs`（项目安装位于 `.agents/` 或 `.claude/`，全局安装加 `--global`），工作目录保持在业务项目根目录；脚本按安装范围共用记录，24 小时内不重复联网，同一候选不重复提醒。有更新时按「统一收尾」作为可选候选简述变化，不阻塞业务任务；用户回复「更新」后，校验原候选为 40 位小写十六进制提交号及原安装范围，并按更新入口的固定模板重建安装命令，不直接执行缓存命令字符串，不临时改装 main 最新版；未知基线明确说明，联网或脚本失败不阻塞任务。检查只读取上游和写入检查记录，不自动安装，不改业务文件。已打开的聊天不假定重新加载新版规则。
- 内部辅助 skill 默认从随包的 `bundled-skills/<name>/SKILL.md`（项目安装时为 `.agents/bundled-skills/<name>/SKILL.md` 或 `.claude/bundled-skills/<name>/SKILL.md`）直接读取，不在菜单注册；可选 skill 未加载时继续，关键 skill 未找到时可退回本机同名版本，均缺失时停在该阶段说明缺什么能力。
- 诊断、需求、方案、独立审查和收尾分别需要 `spot-diagnosing-bugs`、`spot-grilling`、`spot-ponytail`、`spot-ponytail-review`、`spot-verification-before-completion`。只检查当前阶段需要的 skill。
- 阶段交接或最终回复按下文「统一收尾」给出【下一步操作】；工具执行中的进度更新只说明发现与正在做的事，不重复要求用户操作。回复中不报幕所用 skill。
- 「帮我看看」「分析下」默认只读。先核实能查到的事实，再问会改变方案的决定。
- 轻量路径（零次确认）。要求明确、范围小、可逆，且无下述高风险因素，例如修正文案或局部样式，直接修改并验证。
- 中风险路径（一次开工确认）。有行为歧义或范围较大，但影响可控。先核实事实并问清会改变结果的取舍；用户回答澄清问题后，用一张改前/改后草图和简短验收用例同时说明需求和最小方案，再等开工确认。
- 完整路径（两次确认）。涉及权限、金额、日期口径、持久化、迁移、跨模块写入、生产操作，或风险无法排除时适用。用户明确要求完整流程或显式调用 `spot-plan` 且命中上述高危规则时走此路径；若显式调用 `spot-plan` 但无上述高危因素，按中风险路径走一次开工确认。第一次用大白话说明根因，或用一张改前/改后草图说明行为变化，并给出验收标准。第二次标出文件和相关函数，展示一小段核心代码的拟议 diff。验证只列关键回归和容易漏掉的边界（`测什么情况｜应该看到什么结果`，最多 4 行），简单改动用一句话说明怎么验即可。省略上一轮的草图和验收标准。方案如果改变了已确认的行为，单独标出差异。两次都等用户确认，第二次确认后开工。
- 中风险和完整路径共用准备工作。Bug 先用 `spot-diagnosing-bugs` 复现、查根因（连续 2 次定位失败须打临时日志输出入参，3 次未果清空重来防上下文污染）；无法复现就报告证据缺口，可在测试环境临时复现。单点修复需举一反三扫同类隐患。需求用 `spot-plan` 的澄清方法，方案用 `spot-ponytail`。收到适用路径的开工确认后再改业务代码并落测试。发布和部署的授权按发布规则执行。
- 写代码前先查能复用的组件、校验和接口。新增封装、配置或依赖要能对应当前需求。保留清楚的命名、校验和错误处理，行数仅作参考。

## 审查发现多余代码与重构

- 指标异动感知与前置重构：单文件超过 300 行或存在高频变动只触发检查，不直接推荐拆分；确认职责混杂、重复规则等具体维护成本后，按「统一收尾」提供可选重构建议。新需求设计阶段（spot-plan），若目标模块为膨胀/重复重灾区，提供前置轻量重构选项，避开发版紧急窗口。
- 编码收尾时，若本轮改过的手写源码因职责混杂或重复实现，已经造成同一规则要改多处、关键行为难以单独验证等具体维护成本，末尾加一句「重构建议」，点明文件、原因和最小改法。行数可用来筛选候选；实际建议需要代码证据。顺带发现的重构建议由用户决定是否另做。
- 重构实施遵循「原地承接 + 守护防线」：用户确认重构某项时，直接给出「拟议 diff + 既有用例等价性断言」，一次确认即开工，完成后直通 `spot-review`；若目标代码缺乏测试，必须先新增轻量守护测试锁定重构前行为，再给重构 diff 开工。
- 闲置资产与健康整理：在后期维护或全仓瘦身时，由 `spot-refactor` 只读排查孤立文件、死函数、废弃文档、死依赖与僵尸配置，给出零破坏依据（无引用检查与构建校验）后，经用户确认批量安全剔除。
- 审查会话只报告。主会话可在已批准的范围内收掉本次新增的重复逻辑或多余封装，重跑相关验证，确认已约定的行为一致。会改变行为或扩大范围时，先给方案，等用户确认。
- 顺带发现的已有技术债单列报告。需要清理时，另提方案。

## 测试与证据阶梯

- 中风险和完整路径中，每个 Bug 修复都留下可重复运行的回归用例，每个功能需求都留下验收用例。轻量路径按风险验证，简单文案等低影响改动可直接检查结果。
- 优先沿用项目测试入口，严格执行「三级证据降级阶梯」，必须附带终端实际执行输出与退出码 0，严禁口头声明通过；无真实通过证据前禁止在【下一步操作】中推进至 review 或 release：
  - **Level 1（首选）**：项目既有单测/集成测试（如 `npm test`、`pytest`、`go test` 等）。
  - **Level 2（次选）**：静态类型检查与生产构建（如 `tsc --noEmit`、`npm run build`、语法检查），确保改动零破坏。
  - **Level 3（三选）**：零依赖临时探针（使用 Node 内置 `node --test` 或 Python `unittest` 单文件针对病灶断言）。
  - 纯 UI 渲染/样式缺口如实记录浏览器走查结果，并显式标注自动化缺口，不阻断流程流转。
- 回归用例在修复前应因原症状失败，修复后通过，再跑原始复现。功能用例断言用户实际得到的结果。
- 选能触达真实行为的最小测试层。涉及数据库、权限或持久化时，让用例经过相应的真实边界。检查用例实际执行、没有被跳过，且断言能抓住所防的错误。

## 交付与发布

- 自动审查接力：功能需求、Bug 修复、重构或清理在改动完成且验证通过后、交付前，自动读取并执行 `spot-review`，无需用户再次发令，不得仅在【下一步操作】中推荐审查。沿用已确认的要求、本次 diff、验收场景和验证结果，检查需求遗漏、边界与异常路径、上下游调用及旧功能回归；只读检查，证据不足单列验证缺口，不把测试通过当作没有隐藏 Bug。**交付回复中必须包含「审查结论」段落**（显式列出 `[Blocker]`、`[Nit]` 与关键验证缺口判定，全无问题明确写明无阻断项与验证范围），严禁仅凭测试绿灯直接跳过审查结论。普通改动可在当前会话执行；高风险改动（例如金额、日期口径、权限、生产迁移或跨模块写入）自动委派独立审查子代理，交接上述材料并等待结论，不自动创建用户聊天；无独立审查能力时明确报告缺口，不冒充独立审查。审查意见区分 `[Blocker]` 与 `[Nit]`；有阻断项时停止提交与发布，用户回复「修复审查意见」后，主会话直接修复已批准范围内的问题、复测并自动复审，无需重复审批；扩大范围或改变已确认行为时另行确认。复审只看新改动及受影响路径，最多三轮，仍有阻断项则报告并停下。无阻断项时交付审查结论、验证证据和缺口，提交与发布仍按原授权执行。纯文案和局部样式等轻量改动按风险验证，不强制完整审查。
- 阶段性安全审计自适应：能核实基线、范围与已有审计覆盖情况，且未审计的累积提交 ≥ 10 次或新增改动 ≥ 500 行时，按「统一收尾」提供可选审计建议；无法核实时不宣称达到阈值。辅助脚本的计数或提示只作检查线索，不直接证明尚未审计。
- 最终 diff 落定后，用 `spot-verification-before-completion` 的证据核对规则收尾。轻量路径用一句话报告结果与验证；有明显可见变化时用 `spot-before-after-sketch` 展示，另用 1~2 行报告验证和缺口。提交和发布按本任务的授权执行。
- 「准备发布」「发布」「盯部署」走 `spot-release`，支持 GitHub Actions、原生 Git 推送与 npm 包发布等多适配器。发布失败时报告失败步骤和迁移状态，生产重试、迁移和回滚等待用户明确授权。
- 经验沉淀与防呆：不记录无意义流水账。遇到「用户纠偏」、「深坑排查解决」或「阶段性交付新约束」时，提炼 1 句可复用规则草案，按「统一收尾」提供可选沉淀候选；用户确认后用 `spot-learn` 写入项目 rules 或全局偏好。用户说「检查技能更新」时用 `spot-update`。

## 统一收尾

- 所有命令共用本节，只在命令入口保留特定阶段与结果的差异。先自动完成已授权且能执行的必要步骤，再选择提醒；自动接力不扩大修改、提交、发布、重试或回滚的授权范围。
- 按实际状态选择一个首选操作：解决阻断问题 → 补关键证据或信息 → 当前阶段确认 → 已约定的交付。只提出当前可执行、能推进任务的动作；不要跳过前置条件。能自行核实或补齐的事实不交给用户；受环境限制时指出具体缺口与补齐方式。声明自动化缺口的纯 UI 走查按既有例外处理。
- 阶段交接或最终回复正文末尾只有一行 `【下一步操作】`，给一个可复制的极简短语或命令。涉及代码改动的任务在交付前必须先输出审查结论，严禁跳过审查直接给出收尾。当前任务已完成且没有必需的后续操作时，写 `【下一步操作】无需额外操作`，不要求回复「确认完毕」，不默认推荐提交或发布。
- 无阻断问题或关键证据缺口时，最多附带一个有具体依据的可选维护操作，标注「可选」。重构、审计、沉淀与工具更新共用这个名额，按与本次任务的关联、影响和紧迫程度选择；不为凑提醒新增工作。任务已完成时可写 `【下一步操作】无需额外操作；可选：回复「沉淀」`，草案与存储范围先在正文说明。
- 在本次任务对话内去重：同一候选已提醒、已拒绝或已延期且状态未变时不重复提示；用户主动追问、候选或风险变化时再提示。必要的确认请求保持待答，不把沉默视为确认。沿用现有更新限频与去重，不新增提醒状态文件。
- 确认用语明确后果：完整路径第一次用「确认需求」表示进入实现方案，第二次用「开工」表示实施已展示的 diff；一次确认路径用「开工」。发布用「确认发布」，对应已展示的目标、范围与连带动作；已有相应授权就直接继续。缺信息时直接提示补哪项，不用含糊的「继续」。

## 前端

- 局部文案和样式沿用现有组件与设计系统，做一次针对性验证。交互、状态、布局或可访问性有明显变化时，用 `spot-impeccable` 指导设计和检查。
- 整页设计或明显的视觉改版再用 `spot-design-taste-frontend`。两个技能都适用时，共用一次实际页面检查的结果。
- 运行前端辅助脚本时，脚本路径从实际读取的辅助技能目录解析，工作目录保持在业务项目根目录。
- 试用时验证两个 skill 可加载，并保留它们需要的脚本和参考文件。只有实际打开页面检查过，才报告浏览器验证。
