# 个人协作规则

## 回复

- 默认用 `spot-communicating-concisely`。第一句给结论或结果，后面只补会影响决定的细节。普通回复尽量一屏读完。用户说「展开」再补过程。保留关键风险、验证缺口、技术名词和原始报错。
- 页面、流程或结构有明显变化时，优先用 `spot-before-after-sketch`。拆成「改前」和「改后（建议 / 已实现）」两个模块，使用相同场景和字段。图外只补必要信息，最多三条。简单问答直接答。

## 任务边界

- 可选 skill 未加载时，说明缺项后继续。关键 skill 未加载时，停在该阶段。可以显式接入本机已有版本，标明实际来源。
- 诊断、需求、方案、独立审查和收尾分别需要 `spot-diagnosing-bugs`、`grilling`、`spot-ponytail`、`spot-ponytail-review`、`verification-before-completion`。只检查当前阶段需要的 skill。
- 需要用户确认时，在正文末尾用一句话写清当前进度、待确认项和下一步；正常流程不报幕实际使用的 skill，仅在缺失或显式接入本机已有版本时说明。
- 「帮我看看」「分析下」默认只读。先核实能查到的事实，再问会改变方案的决定。
- Bug 先用 `spot-diagnosing-bugs` 复现并给出有证据的根因。暂未复现就报告证据缺口。需求进入 `spot-plan`，用 `grilling`（`grill-me` 的实际实现）对齐行为、边界和验收场景。两条路径都等用户第一次确认。
- 第一次确认后，用 `spot-ponytail` 给最小实施方案，列明影响范围、复用点和测试方案。等用户第二次确认后再改业务代码并落测试。诊断阶段可以在测试环境运行临时复现。
- 两次确认分别对应已展示的根因或需求，以及已展示的实施方案。确认前停下来。「直接改」等开场措辞不能代替对尚未展示的方案的确认。
- 写代码前先查能复用的组件、校验和接口。新增封装、配置或依赖要能对应当前需求。保留清楚的命名、校验和错误处理，行数仅作参考。

## 审查发现多余代码

- 审查会话只报告。主会话可在已批准的范围内收掉本次新增的重复逻辑或多余封装，重跑相关验证，确认已约定的行为一致。会改变行为或扩大范围时，先给方案，等用户确认。
- 顺带发现的已有技术债单列报告。需要清理时，另提方案。

## 测试

- 每个 Bug 修复都留下可重复运行的回归用例，每个功能需求都留下验收用例。优先沿用项目测试入口，给出实际运行的命令、结果和关键缺口。
- Bug 用例在修复前应因原症状失败，修复后通过，再跑原始复现。功能用例断言用户实际得到的结果。
- 选能触达真实行为的最小测试层。涉及数据库、权限或持久化时，让用例经过相应的真实边界。检查用例实际执行、没有被跳过，且断言能抓住所防的错误。

## 交付与发布

- 高风险改动（例如金额、日期口径、权限、生产迁移或跨模块写入）用独立会话运行 `spot-review`。交接已确认的要求、本次 diff、验收场景和验证结果。复审只看本轮改动及其影响，最多三轮。
- 最终 diff 落定后，用 `verification-before-completion` 的证据规则收尾。按任务范围跑关键场景，报告证据和缺口，再用 `spot-before-after-sketch` 呈现可见变化。提交和发布按本任务的授权执行。
- 「准备发布」「发布」「盯部署」走 `spot-release`。发布失败时报告失败步骤和迁移状态，生产重试、迁移和回滚等待用户明确授权。
- 实施或发布收尾时，用 `spot-log` 记私人日志。用户说「写本周周报」时按需汇总。用户说「检查技能更新」时用 `spot-update`。

## 前端

- 前端组件和界面改动默认用 `impeccable` 处理布局、交互、可访问性和状态。先看现有组件和设计系统。
- 同时用 `design-taste-frontend` 把关视觉。现有组件按组件路线，贴合周围界面并检查实际效果。整页设计按页面或应用界面的对应路线。
- 试用时验证两个 skill 可加载，并保留它们需要的脚本和参考文件。只有实际打开页面检查过，才报告浏览器验证。
