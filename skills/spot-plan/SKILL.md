先读取 `../../bundled-skills/spot-grilling/SKILL.md`（未找到时退回本机 `spot-grilling`），用它梳理取舍及其依赖。提问顺序、提问格式和确认时机以本入口下列步骤为准。找不到就报告缺失并停在需求阶段。

1. 先查项目里已有的入口、组件和约束。事实靠检查，影响行为的取舍才问用户。
2. 只问本次需求范围内会改变结果、且未由用户或项目规则明确的取舍。先单独问当前能决定的事项，逐题给推荐答案，等用户回复后再继续。优先调宿主选择题工具；纯文本提问每题限两行（一句话问题 + 推荐答案）。关键取舍都明确后，才展示草图或请求第一次确认。
3. 用 `spot-before-after-sketch` 写一张用户看得懂的行为改前/改后草图，配简短的验收标准。中风险任务把 `spot-ponytail` 的最小方案合进这次展示，等一次开工确认；澄清问题的回答用来确定范围。完整路径用这次展示确认需求，等第一次确认。用户显式调用本技能时走完整路径。
4. 完整路径的第二次确认看实现。用 `spot-ponytail` 拟定最小方案，标出文件和相关函数，用一小段基于现有代码的拟议 diff 展示核心改动。验证只列关键回归和容易漏掉的边界（`测什么情况｜应该看到什么结果`，最多 4 行）。简单改动用一句话说明怎么验即可。省略上一轮的草图和验收标准。方案如果改变了已确认的行为，单独标出差异。等第二次确认后实施。

## 前端专属防漏规则
若涉及组件增加、页面增加或交互/视觉优化，方案设计与验收必须强绑定前端专项技能，不得遗漏：
- **组件增加 / 交互 / 状态 / 布局 / a11y 变化**：读取 `../../bundled-skills/spot-impeccable/SKILL.md`（未找到退回本机 `spot-impeccable`），用其规范指导 UI 结构、微交互、状态处理并纳入验收。
- **整页设计 / 明显视觉改版**：额外读取 `../../bundled-skills/spot-design-taste-frontend/SKILL.md`（未找到退回本机 `spot-design-taste-frontend`），杜绝平庸/AI模板风，并在验收清单中保留真实浏览器打开检查项。
- 方案草图与拟议 diff 中必须显式体现上述技能的落地标准。
