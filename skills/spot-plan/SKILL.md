先读取 `../../bundled-skills/spot-grilling/SKILL.md`（未找到时退回本机 `spot-grilling`），用它梳理取舍及其依赖。提问顺序、提问格式和确认时机以本入口下列步骤为准。找不到就报告缺失并停在需求阶段。

1. 先查项目里已有的入口、组件和约束。事实靠检查，影响行为的取舍才问用户。若涉及目标既有模块且单文件 >300 行或职责混杂，在方案设计与选项中显式提供「前置轻量重构」选项（先抽离脏代码，再写新功能），避免在膨胀模块上直接堆砌逻辑。
2. 只问本次需求范围内会改变结果、且未由用户或项目规则明确的取舍。先单独问当前能决定的事项，逐题给推荐答案，等用户回复后再继续。优先调宿主选择题工具；纯文本提问每题限两行（一句话问题 + 推荐答案）。关键取舍都明确后，才展示草图或请求确认。
3. 用 `../../bundled-skills/spot-before-after-sketch/SKILL.md` 写一张用户看得懂的行为改前/改后草图，配简短的验收标准。
   - **自适应降级（一次确认）**：显式调用本技能时，若未涉及权限、金额、持久化、迁移、跨模块写入等高危因素，把 `../../bundled-skills/spot-ponytail/SKILL.md` 的最小方案拟议 diff 合进本次展示，等一次开工确认。
   - **完整路径（两次确认）**：命中高危因素时，本次展示只确认需求并等第一次确认。
4. 完整路径的第二次确认看实现。用 `../../bundled-skills/spot-ponytail/SKILL.md` 拟定最小方案，标出文件和相关函数，用一小段基于现有代码的拟议 diff 展示核心改动。验证只列关键回归和容易漏掉的边界（`测什么情况｜应该看到什么结果`，最多 4 行）。简单改动用一句话说明怎么验即可。省略上一轮的草图和验收标准。方案如果改变了已确认的行为，单独标出差异。等第二次确认后实施。

## 前端专属防漏规则
若涉及组件增加、页面增加或交互/视觉优化，方案设计与验收必须强绑定前端专项技能，不得遗漏：
- **组件增加 / 交互 / 状态 / 布局 / a11y 变化**：读取 `../../bundled-skills/spot-impeccable/SKILL.md`（未找到退回本机 `spot-impeccable`），用其规范指导 UI 结构、微交互、状态处理并纳入验收。
- **整页设计 / 明显视觉改版**：额外读取 `../../bundled-skills/spot-design-taste-frontend/SKILL.md`（未找到退回本机 `spot-design-taste-frontend`），杜绝平庸/AI模板风，并在验收清单中保留真实浏览器打开检查项。
- 方案草图与拟议 diff 中必须显式体现上述技能的落地标准。

## 实施完成流转（标准闭环）
代码改动完成且验证通过（符合项目测试或证据降级阶梯）后：
- 在【下一步操作】中**默认推荐调用 `spot-review`** 审查本次改动 diff。
- 若 `spot-review` 审查出 `[Blocker]`，用户回复「修复审查意见」时主会话直接修复并复测，无需重复审批方案；全部通过后推进至 `spot-release` 准备发布或直接提交。
