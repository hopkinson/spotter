先读取目标仓库的发布说明、GitHub Actions 触发条件、迁移命令和验证入口。确认仓库、远端、目标分支和发布范围。项目现有工作流决定部署与迁移顺序。

## 准备发布

只做预检。比较已部署或远端基线与待发提交，报告实际比较的范围。运行生产构建和关键回归。检查迁移文件、工作流实际触发条件、兼容性和回滚限制，区分预计执行和已经执行。记录结果、验证的版本和缺口。

工作区混有其他改动时，从待发提交构建隔离副本。浏览器验收应连接待发版本启动的实例，先核对地址和版本。现成开发服务无法证明版本时，使用独立端口。
区分「构建通过」「产物启动通过」「关键业务验收通过」。如果只能用开发服务验证，明确记录生产产物的启动缺口。

## 发布与跟踪

「发布」须有明确的目标和授权。若已有预检，只复跑因待发版本或相关环境变化而失效的检查。已有外部部署时，进入只读跟踪，无需再推送。

1. 发布前确认实际要推送的提交和范围。推送会触发生产迁移时，在预检里明确说明。推送的授权范围必须涵盖该连带动作。
2. 推送后找对应工作流运行。用目标仓库、分支和提交匹配运行，必要时用 `gh run list`、`gh run watch --exit-status` 和 `gh run view`。等待 CI 到终态，记录运行链接和结果。
3. 核对实际部署版本、迁移运行或跳过的结果、线上健康检查和已约定的只读业务验收。CI 的触发 SHA 和实际上线版本可能不同。没有可查证的版本或线上证据就标明缺口。
4. 失败时定位步骤，报告迁移状态和重试或回滚方案。生产重试、手动迁移和回滚须另有明确授权。

收尾区分本地通过、已推送、部署成功待验、已上线并验证。把结果交给 `spot-log`，保留运行链接和版本。
