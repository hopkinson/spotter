先读取目标仓库的发布说明、CI 触发条件、打包脚本、迁移命令和验证入口。确认仓库、远端、目标分支和发布范围。发布范围默认涵盖工作区全部有效改动（包括未暂存、暂存及未跟踪代码）。自动识别发布适配器类型（GitHub Actions / 原生 Git / npm 包）。

## 准备发布

只做预检。检查工作区完整状态（`git status --short`）与未推提交，将当前工作区所有改动与待发提交一并纳入范围报告。在当前工作区运行生产构建和关键回归，确保全量代码构建通过。检查迁移文件、兼容性和回滚限制，区分预计执行和已经执行。记录结果、验证的版本和缺口。

浏览器验收应连接待发版本启动的实例，先核对地址和版本。现成开发服务无法证明版本时，使用独立端口。
区分「构建通过」「产物启动通过」「关键业务验收通过」。如果只能用开发服务验证，明确记录生产产物的启动缺口。

## 发布与跟踪（多适配器支持）

「发布」须有明确的目标和授权。若已有预检，只复跑因待发版本或相关环境变化而失效的检查。已有外部部署时，进入只读跟踪，无需再推送。

1. **发布前确认与工作区全量提交**：
   - 确认实际发布范围（包括工作区未提交文件清单、待推送提交与目标分支）。
   - 获授权后，若工作区存在未提交改动，执行全量暂存并生成原子发布提交（`git add -A && git commit -m "release: ..."`），确保工作区代码整体提交入库，无遗漏。
   - 推送会触发生产迁移或外部发布时，在预检里明确说明。推送授权范围必须涵盖该连带动作。
2. **执行发布适配流**：
   - **GitHub Actions 模式**（存在 `.github/workflows`）：授权后推送，匹配目标仓库、分支与提交的运行，必要时使用 `gh run list`、`gh run watch --exit-status` 和 `gh run view`，等待 CI 到终态并记录运行链接。
   - **原生 Git 模式**（无 GitHub Actions 或私有自建 Git）：授权后执行 `git push <remote> <branch>`，校验远端分支最新 SHA 是否与本地一致，检查 post-receive/webhook 返回。
   - **npm / 库发布模式**（含 package.json 且需发布包）：预检版本号与 `npm pack --dry-run` 文件清单，授权后执行 `npm publish`，核对 npm registry 最新版本。
3. **核对结果**：核对实际部署/发布版本、迁移运行或跳过的结果、线上健康检查和已约定的只读业务验收。没有可查证的版本或线上证据就标明缺口。
4. **异常恢复**：失败时定位步骤，报告迁移状态和重试或回滚方案。生产重试、手动迁移和回滚须另有明确授权。

收尾直接报告本地通过、已推送、部署成功待验或已上线并验证的实际状态，附对应版本、运行链接（如有）、迁移结果和验证缺口；不以推送成功代替上线成功。

## 发布收尾

按公共规则「统一收尾」匹配实际状态，不重复索取已有授权：
- 仅完成准备发布：原任务只是预检时可结束；已约定继续发布但尚缺授权时，展示目标、版本、全量范围及连带动作后提示 `回复「确认发布」`。
- 已获授权且部署仍在运行：继续跟踪至终态，不把等待转交用户。因环境限制无法跟踪时，给出运行链接、缺口和具体查询方式。
- 部署完成待验：能自行执行已约定的验收就继续；确需用户操作时指出具体验收场景及预期结果。
- 发布失败：优先给失败步骤、迁移状态与具体恢复方案；重试或回滚仍需相应明确授权，不能用含糊的「继续」替代。
- 已上线且约定验收完成：自然结束，不追加重复发布操作。
