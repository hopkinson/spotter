先读取 `../../bundled-skills/spot-ponytail-review/SKILL.md`（未找到时退回本机 `spot-ponytail-review`），它是随包锁定的 Ponytail Review。按正确性、安全、负载、测试、性能和精简度的顺序审查。缺失时停止并报告。

- 先锁定仓库、基线和审查范围。使用已确认的需求、验收场景、该任务的 diff 和已有验证结果。工作区有其他改动时排除它们；范围无法区分时先问。
- 读相关调用方和测试。高风险改动优先独立复跑一个最关键的场景，环境缺失时标「待验证」并列出可重复的验证步骤。
- 每条发现都用实际代码和具体输入核对。若怀疑缺校验，先读完整 schema 和入口，diff 中没出现某行不足以证明缺失。无法补齐证据时列为验证缺口。只引用可核实的位置，区分静态推断和实际复现。
- 确认用例有执行，断言能抓到失败，mock 没有绕过关键边界。比如验证数据库时区，要检查真实数据库行为。
- 分级、输出语言和收尾以本入口及公共规则为准；底层审查的 `Must fix / Should fix / Nice to have` 仅作检查线索，不另行输出一套分级，也不直接沿用 `Ship` 结论。严格进行意见分级并按优先级编号：
  - `[Blocker]`：阻断合并（逻辑缺陷、未授权/越权、资损隐患、接口非幂等、重试放大、未捕获的边界崩溃）。
  - `[Nit]`：非阻断建议（局部可读性、命名优化、轻微重复或冗余封装）。
  - 关键测试缺失：已有具体输入和代码证据证明会出错时按 `[Blocker]` 报告；尚不能证明缺陷时列为「关键验证缺口」，不得降为 `[Nit]` 或凭测试缺失断言存在 Bug。
  每条明确给出级别、位置、触发条件、影响和最小修复。若新代码冗余，具体指出可删哪段、复用哪段及如何验证。旧债单列。
- 审查只读。主会话负责已批准范围内的修复和验证。第二轮起看新改动及受影响路径，最多三轮。

## 审查收尾流转
先分别判断代码发现与验证证据，按以下顺序决定下一步：
- 存在 `[Blocker]`：停止提交与发布，在【下一步操作】中明确提示 `回复「修复审查意见」直接修复并复测`，指出修复入口与复测要求。用户确认后主会话直接就地修复、复测并自动复审，无需重复审批方案。
- 无 `[Blocker]` 但有关键验证缺口：仅提供补验证操作，说明缺失场景、可重复的验证步骤和预期结果；不得推荐提交或发布，不把无阻断项说成验证通过。
- 全部通过或仅有 `[Nit]` 且无关键缺口：按原任务约定决定交付、提交或准备发布，沿用已有授权；仅做审查时可自然结束，不默认推荐提交或发布。`[Nit]` 只作为有依据的可选候选，与其他维护提醒共用名额。

验证证据遵循公共规则的三级降级阶梯，必须有实际执行输出与退出码 0，且覆盖本次关键行为；无通过证据、用例跳过、mock 绕过关键边界或只有不相关的绿色检查，均不能消除关键验证缺口。纯 UI 渲染/样式缺口按公共规则如实记录浏览器走查与自动化缺口，不因此一律阻断。审查结论只说明发现与已覆盖范围，不替代提交或发布授权。
